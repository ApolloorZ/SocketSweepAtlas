# SocketSweepAtlas 技术设计

[中文](DESIGN.zh-CN.md) · [English](DESIGN.md) · [面向使用者的说明](../README.zh-CN.md)

这份文档写给要读代码或改代码的人：三层怎么拼在一起、线上协议到底是什么、几个"看起来显然该做"的优化为什么被否掉，以及 README 里每个数字是怎么测出来的。除特别说明，所有数字来自同一台 Redmi K40（Android 13，adb shell 是 uid 2000）、约 25.8 万个文件 / 3.44 万个目录 / 146 GB、走无线 adb。

---

## 1. 整体形状

```
React 19 前端（WebView2 / WKWebView / WebKitGTK）
   ↕  Tauri IPC：30 个命令 + 进度事件
Rust 桥接层（src-tauri/src/lib.rs、pairing.rs）
   ↕  adb 子进程  +  经 `adb forward` 的 TCP 127.0.0.1:5050
C++17 守护进程，跑在手机上（engine/daemon.cpp）
   ↕  opendir / readdir / fstatat，删除走 openat
/sdcard
```

三条原则撑着整个设计：

- **手机是唯一事实来源。** 任何缓存过的扫描结果都不会当作现状显示；一次扫描要么完成，要么明显失败。
- **除了手机，不碰网络。** 程序不监听端口、不做域名解析，`adb` 只连一个转发进设备的回环端口。
- **守护进程是客人。** 它被推到 `/data/local/tmp`，除了 shell 权限什么都没有，会话结束就被杀掉并删除。

## 2. 线上协议

一个连接一条命令，而且每个连接都要先过身份这道门。

```
→ AUTH <64 位小写十六进制>\n
→ SCAN /sdcard\n            ← gzip({"status":"ok","scan_time_ms":…,"scan_threads":4,
                                        "skipped":0,"read_only":false,"tree":{…},
                                        "traverse_ms":…,"sort_ms":…,"serialize_ms":…,
                                        "send_ms":…,"bytes_sent":…})
→ PING\n                    ← {"status":"ok","message":"pong","protocol_version":3,"uid":2000,"read_only":false}
→ DELETE <路径>\n           ← {"status":"ok","message":"Deleted 3 items"}
→ SHUTDOWN\n                ← {"status":"ok","message":"shutting down"}
```

启动命令行是 `daemon <端口> <密钥文件> [--read-only] [--threads 1..8]`。参数不合法就打印 `Usage:` 并以非 0 退出——守护进程绝不带着默认密钥或没有密钥上路。`protocol_version` 由桥接层校验（`lib.rs` 里的 `DAEMON_PROTOCOL`），并且有一条单元测试直接去 `engine/daemon.cpp` 里读那个数字，两边不可能悄悄漂移；版本对不上会被报成"手机上的程序和这个包不是一套"，而不是"连接成功"。

封帧是刻意收紧的：一行只有以 `\n` 结束才算完整，遇到 `\r`、空字节或长度达到 16 KiB 直接判失败。所以 `DELETE /sdcard/a\r\n` 是"失败关闭"，而不是把 `/sdcard/a` 删掉。

每个文件节点都带 `mtime`。它存在的理由是安装包的版本缓存（见下文）和"修改时间"这一列；这是本 fork 加的，上游不发这个字段，所以 `tests/test_daemon.py` 在串行和并行两条路径上都断言它的存在，以后合并时不会悄悄丢。

## 3. 会话密钥

上游的 `515422c` 让守护进程开始要求鉴权，本 fork 要做的部分是让桥接层满足它。

- 每次会话由桥接层现生成 32 字节随机数（`getrandom`），写成 64 位十六进制。
- 密钥通过 **adb 的标准输入**写进手机（`umask 077 && cat > /data/local/tmp/socketsweep_token`），绝不作为命令行参数出现，所以手机的进程列表里看不到它。
- 守护进程读一行、校验形状，然后在接受任何连接之前把文件 `unlink`；删不掉就启动失败。
- 密钥存在一个由互斥锁保护的进程内 `Option<String>` 里；`stop_daemon` 和每一次失败的 `init_daemon` 都会清掉它并删除手机侧文件。没有会话就发命令，直接返回 `E#no_session`，不会带着半套状态往外发。

为什么"只有回环地址"不够：`adb forward` 把这个端口暴露给电脑上任何进程，而一个不会鉴权的旧守护进程会照单全收地删东西。所以不报版本 3 的守护进程被当作**启动失败**处理。

## 4. 扫描根与删除

`engine/safe_delete.h`（上游）把"上一次成功扫描走过的那个目录"钉住：

- `Root::open()` 允许根路径本身是一次符号链接（`/sdcard` 就是），然后保留真实目录的 **fd 和 dev/inode**。
- 删除时从这个 fd 出发，一段一段用 `O_NOFOLLOW` 打开，每一层比对身份，所以父目录被换掉、叶子被换掉都跟不下去；递归删除也绝不穿过子目录里的符号链接。
- 没扫描过就不能删。扫描失败会清掉之前的根。根目录本身和根外面的东西一律拒绝。
- 如果 shell 是 uid 0，守护进程强制 `read_only`——完全禁止删除，并退回串行遍历，做全盘 inode 去重和虚拟文件系统排除。

上游还有一条"不许跨文件系统"：每打开一层目录，就拿它的 `st_dev` 跟**根**的 `st_dev` 比。这条规则在真机上会把应用变成废的：`/sdcard/Android/data` 自己就是一个挂载点（`stat -c %D` 在那里返回 `d2`，而 `/sdcard` 是 `d3`），于是每一个 `Android/data/<包名>` 缓存——也就是最需要删的那一大片——全都报拒绝。现在允许的设备集合改成了"这次扫描实际走到的那些"：`Root` 里带一个 `std::set<dev_t>`，两份遍历器每打开一个目录就把 `info.st_dev` 插进去，`descend()` 改成查这个集合而不是比对相等。扫描之后才冒出来的挂载点、扫描压根没进去的挂载点，依旧拒绝；每一层的 dev/inode 校验一个字没动——所以这道闸仍然是拴在用户亲眼看着跑完的那次遍历上的。

另一半的问题是拒绝得**看得懂**。守护进程回答"删除被拒绝"跟回答"删除成功"用的是同一个姿势——一条正常连接上的 JSON——所以桥接层现在按**前缀**把引擎的话映射成 `E#delete_*` 码（表里 15 条前缀对应 12 个码，加兜底共 13 个：只读、没扫描、在根外、跨文件系统、符号链接、层级过深、目录被改动、权限不足、被占用、已经不在、目录非空、是目录、以及引用手机原话的兜底），措辞全部留在字典里。用前缀而不是整句，是因为部分失败时引擎会在真话后面补一句"some items were removed"，整句匹配会把真正的原因盖掉。以前 UI 只能猜，猜出来的是"该文件可能正在被应用使用"，于是用户去查权限，而老实的答案是"这个位置在另一个文件系统上"。扫描根那条保护前端也自己挡一次（`E#delete_scan_root`），路径压根不发出去。

本 fork 在桥接层补的那一刀是：路径必须**可寻址**——含换行或空字节的路径根本不允许离开电脑（`E#cmd_unsafe`）。

## 5. 目录遍历——以及为什么不用上游那份

在这台手机上读目录是在等，不是在算，而并发遍历实测几乎完全重叠，所以目录被交给一小池读取线程：每个线程读完一个目录，把条目写进这个目录自己的槽位，再把子目录入队。全部读完后由一个线程拼树，逐层把体积加到父目录并按大小排序——排序和折叠的顺序与递归版完全一致，这正是"回答逐字节相同、连并列顺序都不变"的原因。

上游用 `parallel_scan.h` 解决了同一个问题，额外多做一件事：每领一个目录任务，都从被钉住的扫描根一段一段重新打开，每段 `O_NOFOLLOW` 并比对身份。同一台手机、同一份数据、交替三轮并且每轮更换起始顺序，实测：

| 遍历版 | 手机端遍历耗时 |
|---|---|
| 串行参照版 | 24.0 / 9.1 / 10.0 秒 |
| **本 fork 的线程池版（在用）** | **4.5 / 3.4 / 3.2 秒** |
| 上游的锚定版 | 18.4 / 13.4 / 13.5 秒 |

三版结果一致：在不动的 `/sdcard/DCIM` 上摊平后都是同样的 3,022 行；整盘扫描里只有 22 行不同，且每一行都是 QQ 日志在两次扫描之间自己变了大小或时间。也就是说上游那版**又准又慢四倍**——多出来的是 `目录数 × 深度` 次系统调用。

本 fork 留下自己的遍历，并把上游的锚定保护留在**删除路径**上。理由很简单：扫描途中目录被换，最坏是这一次体积报得不准；删除途中目录被换，是丢数据。这段取舍写在了 `engine/daemon.cpp` 的代码旁边，而 `tests/test_parallel_scan.py` 会拿同一个二进制分别以 `--threads 1` 和 `--threads 4` 扫同一批文件并比较解析后的树——以后谁把遍历实现换回去，测试会当场失败。

默认四个读取线程（`cfg::DEFAULT_SCAN_THREADS`），并按 CPU 核数封顶，可用 `--threads 1..8` 覆盖。四是实测拐点。

## 6. 压缩，以及"活得过压缩"的分段计时

`JsonStream` 把回答直接写进一个 gzip 成员（`deflateInit2(16+15)`、64 KiB 输出缓冲、攒到 32 KiB 推一次），于是 57.5 MB 的回答在线上变成 9.3 MB。如果 zlib 起不来，就退回明文并在 stderr 说明——慢一点可以接受，扫坏不行。桥接层嗅探 gzip 的两个魔数字节，而不是假设一定是压缩的。

分段计时取在**压缩器内部**，这是容易搞错的地方：开着压缩时，序列化"结束"的那一刻，树的大部分还留在 zlib 缓冲里。所以 `out.sync()` 做的是一次 `Z_SYNC_FLUSH`——把缓冲推出去、把 deflate 攒着不发的部分也吐出来，但不关闭 gzip 成员——这样 `send_ms` 和 `bytes_sent` 覆盖的是整个载荷，而读取方拿到的仍是一个完整合法的流。真正的收尾在 `finish()`；写被截断会记成"答案不完整"。

手机实测：遍历 2.3 秒、排序 0.03 秒、序列化 0.6 秒、送隧道 0.05 秒、线上 9.3 MB。无线 adb 大约 2.4 MB/s，USB 大约 38 MB/s——所以现在托底的已经不是文件系统，而是线路。

## 7. Rust 桥接层

- **所有碰手机的命令都是 `async`**，包括连接过程中每 150 毫秒轮询一次的 `ping_daemon`。
- `DAEMON_OPERATION` 把会话变更（启动、停止、重连）串行化。`run_scan` **故意不持这把锁**：它可能比一次重连活得更久，而 `std::mutex` 不可重入——恢复路径里调用的 `init_daemon` 才需要拿锁。
- 回答在被相信之前先被检查：空正文、不是 JSON 对象、解压失败、以及"手机说扫到 0 个文件但其实有数据"，各是一个独立的错误码，前三种会触发一次自动重启重扫。
- 文件名必须是合法 UTF-8：桥接层拒绝把有损解码过的树交给前端，因为一个被改坏的路径既打不开也删不掉。
- `peek_file` 读的是字节区间（`offset` + `limit`，上限 2 MB）而不是整个文件。预览读头部，安装包读取尾部。块数被夹住时不能悄悄丢掉最后一段——那个 bug 丢掉的正是文件末尾几百字节，也就是 zip 索引的目录结束记录所在的地方。
- `df` 的输出按不可信处理：空回答是 `E#df_empty`，不是 panic，也不是一句英文。

## 8. 前端

| 模块 | 职责 |
|---|---|
| `App.tsx` | 连接流程、扫描调度与计时、日志与错误卡 |
| `ResultView.tsx` | 三种视图（总览 / 目录 / 类型）、表格、选择、整行占比底色、空间弹窗、滚动记忆 |
| `opener.ts` | 打开/下载/上传/移动/删除、队列与取消、空间预检、缓存台账 |
| `thumbs.ts`、`Thumb.tsx` | EXIF 缩略图挖掘、data URI、懒挂载与并发上限 |
| `apkFormat.ts`、`apkInfo.ts`、`ApkVersion.tsx` | zip 索引与二进制 XML 的纯解析、按段读取与落盘缓存、懒加载单元格 |
| `i18n.ts`、`messages.ts` | 语言上下文与全部文案（含后端错误码） |
| `settings.ts` | 设置读写、默认值、颜色合法性 |
| `mockScan.ts` | 只在浏览器里生效的假后端（`isMockMode`） |

改它之前要知道的两件事：

- **行是逐步挂载的。** `shown` 随视口增长，`useLayoutEffect` 在进入子目录再返回时同时恢复滚动位置和已挂载行数，所以 25 万个节点永远不会变成 25 万个 DOM 节点。
- **类型分桶只有一处，依据是扩展名。** 测试台的假文件因此按类型命名（`.mp4`、`.mp3`、`.apk`、`.pdf`、`.zip`）——一份全是 `.jpg` 的夹具根本无法覆盖视频、音频、文档、压缩包和安装包这几条路径。

### 安装包版本

`versionName` 不在文件名里，也不在目录列表里：它在 `AndroidManifest.xml` 里，而 APK 内的这个文件是一段**二进制** XML，位置记在文件**末尾**的 zip 索引里。所以读取顺序是：先在中央目录里查一个名字（窗口从 256 KiB 翻倍到 2 MiB，起点必须落在块边界上，否则末尾会被截掉），再读本地文件头找到数据起点，用浏览器自带的 `DecompressionStream("deflate-raw")` 解原始 DEFLATE，最后走一遍字符串池和根元素那张属性表。`versionName`（类型 `0x03`）和 `versionCode`（类型 `0x10`）都会读，给人看的那个优先。

这里没有任何猜测：凡是不完全符合格式的形态一律返回 null、单元格留空，因为一个"看着合理但错了的版本号"比没有更糟。答案按 `apk-<fnv1a(路径)>-<size>-<mtime>` 落盘缓存；**只存成功读到的答案**，所以今天读不出来的安装包明天还会再试一次，而不是被永久冻成空白。

### 错误码与语言

后端从不发用户会读到的句子，只发 `E#code` 或 `E#code#详情`，措辞全部在 `messages.ts` 里，两种语言成对存放。日志条目保存的是**键 + 参数**而不是写死的句子，所以切换语言时屏幕上已有的条目会一起改措辞。盯这件事的审计脚本必须同时匹配 `format!` 和裸英文字面量——只查前者时，曾经给出过一个自信的"0 处未翻译"，而那是错的。

## 9. 电脑上的三个缓存目录

三个文件夹、三种生命周期、都可改位置，默认落在软件自己旁边的 `data/` 而不是系统盘：

- **cache**：你在电脑上打开过的文件副本。有容量上限、按最旧先淘汰、可选退出时清空。
- **thumbs**：挖出来的图片预览和安装包版本。独立上限、独立清空按钮。
- **downloads**：只有你明确点过下载的文件。永不自动清理，也绝不当作缓存。

键名是设备路径的哈希，再带上体积和 `mtime`，所以手机上文件一变，就不可能再命中旧条目。

## 10. 性能演进

| 阶段 | 整盘扫描（热缓存） | 手机端遍历 | 线上字节 |
|---|---|---|---|
| 接手时 | 约 74 秒 | 约 33 秒 | 57.0 MB |
| + 回答压缩（仍单线程） | 21–35 秒 | 24.6 秒 | **9.2 MB** |
| + 并行遍历（本 fork） | **6–10 秒** | **2.4–4.5 秒** | 9.2 MB |

守护进程内存峰值：四线程 97.5 MB，单线程 79.0 MB；剥符号后二进制 797 KB。"内存是平的"这个说法只对那 64 KiB 序列化缓冲成立：**整棵树是先在手机内存里建完，才发第一个字节的**——这也正是扫描中途不可能有中间结果的原因。要做流式输出，得先把遍历重新设计（上游 issue #9）。

关于测法，都是踩过坑换来的：手机自己的元数据缓存会让冷扫比热扫慢三到五倍，所以**本文所有对比都是交替、多轮、并且每轮更换起始顺序**；比较的对象是摊平后的树（深度、类型、体积、mtime、完整路径），不是总数。第一次做并行遍历基准时得出过"单线程 74 秒"的荒谬数字，因为脚本 fork 了 4,096 个 `find` 进程；也有一次"修好了"的结论来自一个忘了重新拷贝的旧安装包。

## 12. 构建与打包

- `engine/build.sh` 用 `aarch64-linux-android31` 交叉编译，带 `-static-libstdc++ -s`，链接 NDK sysroot 里的 `libz.a`（找不到退回 `-lz`），然后把产物拷到 `src-tauri/bin/daemon`——打包器只认后面那份，忘了拷就等于发布了一个旧守护进程，这种事真的重复发生过。
- CI 三条腿：Linux（ubuntu-22.04，为了让 glibc 下限低）、macOS、Windows，三层测试全跑，打 tag 时产出草稿 Release。AppImage 那一腿会修 `.DirIcon`、把 `tauri-bundler` 留成 0700 的目录权限改回来，并写入由 `GITHUB_REPOSITORY` 推导的 `gh-releases-zsync` 更新信息——这样分支仓库不会去跟上游的 Release 更新。
- Windows 只出 NSIS。要不要带 `WebView2Loader.dll` **取决于工具链**，这一点本 fork 内部就搞错过一次：`webview2-com-sys` 0.38.2 在 `target_env = "msvc"` 下选的是 `link(name = "WebView2LoaderStatic", kind = "static")`，只有非 MSVC 分支才 `link(name = "WebView2Loader.dll")`。所以 CI 的 MSVC 构建不需要在可执行文件旁边放任何东西；而我们的 GNU 构建，`objdump -p` 的导入表里确实写着这个 DLL，安装包必须带上它——这就是被 gitignore 排除的 `src-tauri/webview2/WebView2Loader.dll` 和覆盖文件里那一条的由来。教训是：**一份构建产物的导入表，不能拿来当另一套工具链的证据**。打包器还会强制每个 Tauri 插件的 npm 包与 crate 次版本号一致——这就是 `@tauri-apps/plugin-opener` 被钉死版本的原因。
- **免安装的 Windows 版就是同一个 exe 加一个标记文件。** `scripts/portable-win.ps1` 把 `tauri-app.exe`、四个随附文件和 `portable.txt` 装进一个 zip。程序启动时、窗口建出来之前先去 exe 旁边找那个标记：找到了就把 `WEBVIEW2_USER_DATA_FOLDER` 指到同目录的 `data\webview2`（设置真正住的地方——主题、语言、排序、下载台账全在 localStorage 里），`window.json` 也写在那里而不是 `%APPDATA%`。两处是有意为之：判定用 `is_file` 而不是 `exists`，免得一个同名目录把安装版的设置搬走；目标目录用"写得进去"来确认而不是假设，所以只读 U 盘会退回默认位置，而不是启动失败。安装包里没有这个标记，已安装的用户完全不受影响。
- 版本号写在 `package.json` 和 `tauri.conf.json`；推 tag 时 CI 会用 tag 覆写这两处。

## 13. 已知限制，以及有意不做的事

- **扫描中途没有中间结果**，也不做"先显示上次的、后台再刷新"：屏幕上的数字必须描述手机此刻的真实状态。
- **不做按目录 mtime 的增量扫描。** 遍历只剩 3 秒以后，收益天花板太低，而代价是可能显示过期体积，与上一条冲突。
- **不引入流式扫描协议和扫描存储。** 上游在本 fork 的合并点之后把两者都做了；要接进来必须把回答格式和建树步骤一起重新规划，而本 fork 的测量说，现在到顶的是线路而不是遍历。
- **不自定义扫描目录**——不先扫全盘，你根本不知道该选哪些子树。
- **不换二进制协议。** 下一个真正的收益点是"少发字节"（只发文件名、由电脑侧按目录重建路径），这在 JSON 里就能做。
- 安装包版本列只覆盖这一种文件类型。视频/音乐时长做过评估后放弃：每个格式都要单独的解析器，而这行的高度不值这个钱。
